# Init Task Architecture

<!-- markdownlint-disable MD013 -->

## Contract

Init Task Architecture defines Hideout first-run initialization, safe repairs,
helper setup, schema/version metadata repair, backend preparation, and project
bootstrap.

This document follows:

- [architecture-principles.md](architecture-principles.md)
- [distribution-bootstrap.md](distribution-bootstrap.md)
- [manager-control-plane.md](manager-control-plane.md)
- [ecosystem-foundation-design.md](ecosystem-foundation-design.md)

The product supports initialization tasks. It does not support arbitrary
initialization scripts.

## Core Principle

Initialization is managed authority.

Initialization can create profile state, materialize identity, install helper
binaries, repair current schema metadata, prepare backend metadata, write
project manifests, and repair local state. These are authority-changing
operations and must use the same product contract as other privacy boundaries:

```text
detect -> plan -> review -> apply -> verify -> audit
```

No first-run path may execute untyped shell, host commands, bundle install
scripts, project scripts, or unrestricted goja.

## Three Separate Concepts

### InitTask

`InitTask` is a typed Manager-owned task for product initialization or repair.
It is visible, idempotent where practical, auditable, and retryable.

Examples:

```text
store.create
profile.create
identity.materialize
schema.metadata.write
helper.locate
helper.install
backend.probe
backend.prepare
environment.prepare
command.expected.check
doctor.fix.safe
project.manifest.create
project.manifest.apply
```

### SessionBootstrap

`SessionBootstrap` is the per-run bootstrap generated by Hideout for a specific
session. It may create guest shims, mount runtime directories, start HostFS
guest daemons, or configure session network state.

Session bootstrap is not user-authored. Bundles and project manifests cannot
write it directly. Every run regenerates session authority even when the
environment is warm.

### Bundle Script

Bundle scripts are constrained goja policy entrypoints. They may propose policy
decisions inside a fixed ABI. They cannot initialize Hideout, mutate profiles,
install software, run shell, access filesystem, access network, or write session
bootstrap files.

## Domain Model

```text
InitRequirement
  declared need from product, project, bundle, backend, or doctor

InitPlan
  ordered plan with typed InitTasks, risk labels, inputs, outputs, and review

InitTask
  one typed action, idempotent where practical and safe to re-run

InitRun
  execution record for one applied plan

InitResult
  final status, changed resources, audit refs, and follow-up actions
```

Minimum `InitTask` fields:

```text
id
kind
source
status
targetScope
capabilityBoundary
risk
inputs
outputs
idempotencyKey
requiresConfirmation
auditRef
```

Tasks follow one convention instead of per-task mode fields: every task is
idempotent by default and safe to re-run, and verification and repair behavior
belong to the task kind.

Allowed `source` values:

```text
builtin
doctor
backend
project
bundle
local-dev-override
```

`project` and `bundle` sources may declare requirements or hints. They must not
provide executable task bodies.

A project or bundle may also declare a guest base image reference — an image
name plus digest. Manager compiles that declaration into a typed
backend-prepare task with digest verification and environment-fingerprint
compatibility checks. A bad image is contained by the backend boundary, so the
declaration is guest-domain data rather than host authority; it never becomes
an executable task body.

## Phase 1 Task Set

Phase 1 should stay small.

Allowed safe tasks:

```text
store.create
profile.create
identity.materialize
schema.metadata.write
helper.locate
helper.install.linux-shim
helper.install.linux-hostfsd
helper.install.linux-session-supervisor
backend.probe
network.mode.select
doctor.check.light
doctor.fix.safe
project.manifest.create
```

Allowed tasks with explicit confirmation:

```text
helper.install.official
backend.template.download
doctor.fix.permissions
doctor.fix.stale-session-cleanup
project.manifest.apply
bundle.install.confirm
```

Design-ready but not Phase 1 default:

```text
system.backend.install
system.tun.prepare
browser.profile.create
backend.image.verify
environment.deep-prepare
```

`backend.image.verify` is the compiled form of a declared guest base image
reference: it fetches or locates the referenced image, verifies its digest,
and checks environment-fingerprint compatibility before backend prepare uses
it.

Disallowed:

```text
host.shell
host.exec
guest.shell
curl.pipe.shell
bundle.installScript
project.initScript
raw.mount
raw.networkRoute
sudo.auto
shellRc.modify
gitConfig.modify
sshConfig.modify
browserProfile.import
profileAuthority.autoGrant
```

A declared guest base image reference is not on this list: referencing an
existing image is data consumed by backend prepare, not a step Hideout
executes. Ecosystem-supplied imperative preparation steps — install scripts,
first-boot hooks, provisioning fragments — stay disallowed until a dedicated
trust design.

## First-Run Flow

The primary user path remains:

```bash
hideout run -- example-cli
```

If required initialization is missing:

```text
hideout run
  -> PlanInit(scope=machine, project=current workspace)
  -> apply safe non-interactive tasks
  -> present tasks that require confirmation
  -> continue run only after required tasks are applied
```

In non-interactive environments, missing confirmation fails with a clear next
step:

```bash
hideout init --template dev --profile default --backend native --network direct --no-input
hideout doctor --fix --dry-run
```

Explicit initialization remains available:

```bash
hideout init
hideout init --template privacy --profile default --backend lima --network tun2socks --proxy-secret <ref> --mediated-resolver <ip> --no-input
hideout doctor --fix --apply
```

`auto` and omitted backends resolve to the same backend as `hideout run`: Lima
on supported macOS hosts. Hosts without a supported product backend fail closed
instead of implicitly selecting a weaker backend. The weak native backend is
available only when the operator explicitly selects `--backend native`.

## Product Command Scope

Keep the command model narrow.

Machine setup:

```bash
hideout init
hideout doctor
hideout doctor --fix --dry-run
hideout doctor --fix --apply
```

Project setup:

```bash
hideout project init
hideout project diff
hideout project apply
```

Bundle lifecycle:

```bash
hideout bundle install <source>
hideout bundle list
hideout bundle verify <name>
hideout bundle remove <name>
```

`bundle update` and `bundle rollback` are later increments.

Profile commands should focus on identity, clone, rotate, path, diff, and
explain. Bundle lifecycle should stay under `hideout bundle`.

## Manager Operations

```text
PlanInit(scope, profile, project, backend, flags) -> InitPlan
ApplyInit(planId) -> InitRun
GetInitRun(runId) -> InitResult

PlanDoctorFix(checks, scope) -> InitPlan
ApplyDoctorFix(planId) -> InitRun

PlanProjectInit(projectPath) -> InitPlan
ApplyProjectInit(planId) -> InitRun
```

All operations are local-only by default and must produce redacted plan output
that CLI, TUI, and WebUI can render.

## TUI And WebUI

Phase 1 uses CLI `hideout init` and
`hideout doctor --fix --dry-run|--apply` as the product init surface.
`hideout init --template ... --no-input` is the scripting and CI path. A future
TUI wizard must still use this same InitTask plan/apply engine; it must not
create a second initialization model.

The TUI first-run wizard should stay within five steps:

```text
backend detection and recommendation
helper binary check or install
default profile and identity initialization
network mode selection
project Hideoutfile and bundle permission diff
```

WebUI should not be required for first successful run. The current WebUI smoke
surface can render Manager init plans and controlled applies. Richer audit
exploration, policy editing, bundle permission review, and network
explanations remain future product work through Manager API.

## Audit

Every applied init task records:

- action;
- task ID;
- task kind;
- source;
- target scope;
- risk label;
- touched host paths, redacted where needed;
- artifact version and digest, when relevant;
- signature or checksum status, when relevant;
- whether network download was required;
- whether confirmation was required and received;
- changed Manager resources;
- verification result;
- rollback or repair result.

Audit must not record secret values, proxy URLs with credentials, broker tokens,
private key material, or raw identity material.

## Failure Behavior

Init fails closed when:

- task kind is unknown;
- task source is untrusted for the requested action;
- a project or bundle provides an executable init body;
- a task requires shell execution;
- artifact checksum or signature verification fails;
- helper binary source is unverified;
- non-interactive mode encounters a task requiring confirmation;
- an init task would add runtime authority without Manager plan/apply;
- a task attempts to mutate profile identity, HostFS grants, mounts, network
  routes, OpenTarget, PortBridge, or overlay apply outside its declared action.

Warnings may be used for trust level or optional optimizations. They must not be
used for missing privacy contracts.

## Release Gates

Minimum acceptance:

- `hideout init --template dev --profile default --backend lima --network direct --no-input` plans the default Lima first-run
  path, including Linux guest helper tasks when official helpers are missing;
- `hideout init --template dev --profile native-dev --backend native --network direct --no-input` creates store
  directories, default profile, identity state, schema metadata, and runtime
  directories under a temporary store for the explicit weak-isolation smoke;
- repeated doctor repair is idempotent, while template-aware `hideout init`
  rejects an existing profile instead of rotating identity or granting new
  authority;
- `doctor --fix --dry-run` shows safe fixes without applying unsafe actions;
- expected-command diagnostic inputs compile into explicit typed diagnostic
  tasks that report command presence, not install scripts, raw profile writes,
  or any package-manager assumption;
- init plans include structured `nextSteps` entries for doctor verification,
  smoke runs, configured generic CLI commands, or blocked-task resolution;
- `hideout init --template privacy --network tun2socks --proxy-secret <ref>
  --mediated-resolver <ip>` compiles proxy and DNS mediation configuration into
  `network.mode.select`, persists only non-secret references, and fails closed
  when the ref or resolver is missing or invalid;
- helper discovery succeeds from official store path or explicit development
  override and fails closed when the binary is missing or mismatched;
- store-built helpers have sibling `hideout.helper-manifest/v1` manifests, and
  default store helpers without a current manifest remain pending repair;
- `hideout init --backend lima` validates prerequisites and generated backend
  metadata without starting the VM unless a deep check is explicitly requested;
- session bootstrap files, broker tokens, and network bootstrap remain
  per-session and are not persisted by init;
- project and bundle init requirements compile into a plan, not executable
  scripts;
- init audit records task source, kind, result, and changed resources as
  `hideout.init-audit/v1` JSONL in `logs/init-audit.jsonl` without leaking
  secrets. `hideout init` emits `init.apply`; automatic lightweight
  store/profile/schema metadata setup during `hideout run` emits
  `run.init.apply`; `doctor --fix --apply` emits `doctor.fix.apply`; dry runs do not
  write audit.

## Phase Plan

### Phase 1 Foundation

- define InitTask model and Manager operations;
- implement safe machine initialization for `store.create`,
  `schema.metadata.write`, `profile.create`, `identity.materialize`,
  `network.mode.select`, `backend.probe`, `helper.install.linux-shim`,
  `helper.install.linux-hostfsd`, `helper.install.linux-session-supervisor`, and
  `doctor.check.light`;
- make `doctor --fix --dry-run` and safe `doctor --fix --apply` use the same task
  engine;
- keep bundle/project requirements declarative;
- add static gates and native development harness gates.

### First Product Increment

- interactive TUI wizard;
- helper official install flow;
- project init/diff/apply;
- bundle install confirmation through Manager plan/apply.

### Later

- system backend installation guidance;
- signed helper downloads;
- binary extension model, only after a separate security design.
