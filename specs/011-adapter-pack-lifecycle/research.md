# Research: Adapter Pack Lifecycle And Local Registry

<!-- markdownlint-disable MD013 -->

## Decision 1: Store-Wide Registry With Profile-Pinned Enable Bindings

**Decision**: Store installed packs once in a store-wide registry. Profiles hold
explicit enable bindings that pin exact pack lock/revisions plus command and
capability bindings.

**Rationale**: 011 needs reusable packs without turning installation into
authority. Existing 008 profile config lives directly under
`profile.CommandAdapters` (`internal/profile/profile.go:138-151`) and runtime
compile only includes enabled adapters (`internal/cmdadapter/profile.go:41-63`).
Keeping profile binding as the authority edge preserves that model while
removing duplicated script artifacts.

**Alternatives considered**:

- Profile-local registry only: simpler, but duplicates packs and makes upgrade
  evidence harder to reason about.
- Store-wide latest tracking: convenient, but violates the requirement that
  upgrades cannot silently change active profile behavior.

## Decision 2: Exact Revision Pinning For Active Bindings

**Decision**: Profile enable bindings pin one exact pack lock/revision. Upgrade
creates a new candidate revision; active profile behavior changes only after
explicit profile re-enable.

**Rationale**: 008 currently verifies a digest before invoking a profile adapter
(`internal/cmdadapter/profile.go:81-91`). 011 should preserve that strictness at
pack granularity. Binding to latest would make upgrade a hidden profile
authority change.

**Alternatives considered**:

- Track latest validated version: easier UX but weakens operator review.
- Per-binding latest or pinned mode: more flexible but adds a policy mode before
  there is demonstrated need.

## Decision 3: Core-Owned Built-Ins With Pack-Compatible Metadata

**Decision**: Built-in adapters remain Core-owned and immutable, but expose
pack-compatible metadata for list, inspect, test, and evidence surfaces.

**Rationale**: The root-sensitive built-in is currently generated by Go
(`internal/cmdadapter/profile.go:133-152`) and carries non-claim behavior.
Moving it into mutable registry storage would blur Core-owned evidence and
operator-installed code.

**Alternatives considered**:

- Materialize built-ins as registry files: unifies display but creates fake
  mutability and new tamper states.
- Keep built-ins invisible: avoids registry work but hides an important adapter
  from users and doctor/status surfaces.

## Decision 4: System Git For Exact-Commit Source Intake

**Decision**: Use the system `git` executable for git-source installation in
011. Require exact commit ids. Do not enable recursive submodule checkout by
default. Do not treat local hook/filter configuration as authority. Lock the
checked-out tree by digest before tests or enablement.

**Rationale**: The project currently has a small dependency set and no git
library. Using system git keeps 011 focused on lifecycle and lets future doctor
report missing git. The real safety boundary is digest lock plus constrained
Goja plus proposal-only runtime, not git as a trusted executor.

**Alternatives considered**:

- Add a pure-Go git dependency immediately: improves portability but expands the
  dependency/supply-chain surface before alpha needs it.
- Local path only: simpler, but the operator already accepted pinned git
  sources for 011.

## Decision 5: Core Validation Is Primary; Pack Tests Are Secondary

**Decision**: Enablement requires both Core validation and pack test success.
Core validation is primary and cannot be bypassed by passing pack-authored
tests.

**Rationale**: Pack tests are authored by the pack and may be incomplete or
malicious. Existing 008 runtime already validates outcomes and allowed
capabilities in Go (`internal/cmdadapter/outcome.go`, referenced by tests in
`internal/cmdadapter/outcome_test.go`). 011 must keep that as the security
gate.

**Alternatives considered**:

- Treat pack tests as sufficient: unsafe because the pack can self-certify.
- Make pack tests optional: loses a useful quality gate before enablement.

## Decision 6: Deterministic Pack Test Harness Reuses Goja Constraints

**Decision**: Run pack tests through the same constrained script runtime and
adapter outcome validation used by runtime evaluation. Tests feed fixed command
contexts and expected outcomes; no filesystem, network, process, timer, backend,
broker token, HostFS apply, or profile mutation APIs are exposed.

**Rationale**: 008 already routes adapter evaluation through the existing policy
runtime and strict outcome validation. A separate test VM or Node runtime would
create a second ABI that can drift from production.

**Alternatives considered**:

- Run tests with Node.js: faster ecosystem familiarity but violates the no-node
  constraint and would not prove Goja behavior.
- Static manifest-only checks: insufficient because adapter output behavior is
  part of the contract.

## Decision 7: Registry State Is File-Backed JSON With Atomic Writes

**Decision**: Store pack registry, locks, test results, and lifecycle state as
schema-validated JSON under the Hideout store using atomic write semantics.

**Rationale**: Profiles, schemas, and existing Manager plan/apply flows already
use local file-backed state. 011 does not need a database. Atomic writes and
schema validation are enough for a single-operator local registry.

**Alternatives considered**:

- Embed registry directly in profiles: duplicates installed pack metadata and
  makes store-wide revoke hard.
- Add a database: unnecessary operational surface for alpha.

## Decision 8: Manager Lifecycle Surface Extends 008 Plan/Apply

**Decision**: Add Manager lifecycle operations for pack install, test, enable,
disable, upgrade, revoke, list, and inspect. Existing 010-style typed plan/apply
semantics apply to authority-changing operations; list/inspect are read-only.

**Rationale**: 008 already has `PlanCommandAdapter` and `ApplyCommandAdapter`
for profile adapter mutation (`internal/manager/command_adapters.go:57-218`).
011 should not introduce raw profile writers or UI-owned authority.

**Alternatives considered**:

- CLI-only registry edits: violates the Manager control-plane direction.
- Direct profile JSON edits: bypasses validation and evidence.

## Decision 9: Runtime Compile Resolves Pack Bindings Into 008 RuntimeAdapter

**Decision**: Keep the broker/runtime execution path stable. Registry-backed
profile bindings resolve into the existing `cmdadapter.RuntimeAdapter` shape
before `broker.handleCommandAdapter` executes.

**Rationale**: `broker.handleCommandAdapter` already expects a compiled runtime
and validates route, command ownership, context, outcome, and evidence through
the 008 path. Reusing that path reduces authority drift and keeps existing tests
valuable.

**Alternatives considered**:

- Add a second broker action for packs: duplicates validation and audit logic.
- Evaluate packs directly from Manager: puts runtime decisions in the wrong
  surface.

## Decision 10: Evidence Reuses Audit And Export Boundaries

**Decision**: Pack lifecycle events emit local audit details and export/share
references through the existing deterministic redaction/export boundary.

**Rationale**: 005 established the export boundary, and 008 already emits
adapter evidence. 011 adds lifecycle evidence but must not invent a separate
redaction contract.

**Alternatives considered**:

- Keep pack lifecycle local-only: weakens support/debuggability.
- Export raw registry files: risks control-plane path leakage and skips
  redaction rules.
