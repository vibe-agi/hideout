# Implementation Plan: Guest Privilege Separation And Risk Audit

<!-- markdownlint-disable MD013 -->

**Branch**: `009-guest-privilege-separation-risk-audit` | **Date**: 2026-07-08 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/009-guest-privilege-separation-risk-audit/spec.md`

## Summary

009 adds a per-run guest privilege status and, for Lima, a real dual-identity
path: target commands run as a non-root, non-sudo user while Hideout privileged
setup uses a Go-owned setup identity. If the selected image or existing
environment still grants passwordless sudo to the target user, Hideout reports
`degraded`, warns, audits, and avoids root-containment claims.

The implementation centers on a new privilege-status model, Lima setup-identity
provisioning, replacement of shared `sudo -n` setup scripts, and evidence
surfacing across audit, Boundary Summary, explain/doctor, Manager overview,
TUI/WebUI, and real Lima gates.

## Technical Context

**Language/Version**: Go 1.25.x, shell snippets generated by Go for guest setup.

**Primary Dependencies**: Existing Lima backend, manager core, audit writer,
Boundary Summary builder, network bootstrap, HostFS daemon, command adapter
runtime, and JSON schemas.

**Storage**: Existing profile, environment, session, runtime, audit JSONL, and
Lima instance files. New setup identity material lives under Hideout control
storage, never in target-writable guest paths.

**Testing**: `go test ./...`, Gate 0, targeted Lima unit/fake-runner tests, real
Lima enforced/degraded proof, and Gate 3 when DNS/tun2socks setup changes.

**Target Platform**: Product proof is macOS host with Lima. Native backend is
status-only/unknown and remains a weak development harness. Linux host support
can share status/data-model code but is not the enforced proof target for v1.

**Project Type**: Local CLI/TUI/WebUI/daemon application with backend adapters.

**Performance Goals**: Privilege checks run once per run/environment resume and
must not add more than a small setup-time delay to normal command startup.
Evidence rendering must remain bounded by existing overview/audit caps.

**Constraints**: No JavaScript authority, no raw target sudo, no silent fallback
from requested privileged setup to a broken path, no in-place trust upgrade of
pre-009 environments, and no root-containment claim in `degraded` or `unknown`.

**Scale/Scope**: Single local operator, one run/session at a time per command.
No organization policy, delegated approval, marketplace trust, or package
installation apply path in 009.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Privacy Boundary**: Touches backend, network, DNS, HostFS setup, profile,
  environment lifecycle, command proxy evidence, cleanup, and UI status.
  Requested privileged setup fails closed when no allowed setup path exists.
  `enforced` cannot be emitted without complete proof.
- **Typed Authority**: Go Core/backend owns setup identity provisioning,
  privilege checks, status classification, setup execution, validators, audit,
  and display state. JavaScript adapters remain intent capture only and cannot
  execute guest privilege.
- **Workspace And Policy**: Workspace semantics do not change. HostFS remains
  read-only in 009. Setup credentials and scripts are Hideout control-plane
  material and must not be grantable through HostFS or target-writable mounts.
- **Generality And Provider Scope**: Lima root/control identity is the v1
  backend mechanism. Sudo/package-manager commands are evidence examples, not
  Core semantics.
- **Evidence And Redaction**: Adds privilege status and setup events to audit,
  Boundary Summary, explain, doctor, Manager overview, TUI/WebUI, and export
  paths through existing deterministic redaction.
- **Backend And Distribution**: Lima proof is required. No new product helper
  binary is planned for v1; root/control SSH is preferred over a new guest
  helper. Native remains weak/unknown.
- **Gates**: Gate 0 for schemas/docs/unit tests. Real Lima Gate 2-style proof
  for enforced/degraded statuses. Gate 3 must pass if tun2socks/DNS setup is
  modified.
- **Status And Docs**: Update `docs/STATUS.md`,
  `docs/privacy-run-design.md`, `docs/threat-model.md`,
  `docs/privacy-run-test-plan.md`, `docs/backend-capability-matrix.md`, and
  `docs/network-privacy-architecture.md` if setup paths change.

**Pre-Design Gate**: PASS. 009 strengthens fail-closed setup and evidence
without moving authority into scripts or UI.

## Phase 0 Research Summary

Research output: [research.md](research.md)

Key decisions:

- Lima enforced status uses a Hideout-owned root/control SSH setup path created
  by system provisioning; target commands continue through the profile user.
- Existing environments are not upgraded in place; they remain `degraded` or
  `unknown` until recreated.
- Requested privileged setup fails closed if it cannot use an allowed setup
  path.
- `degraded` is warning/audit by default; enforced-only is a profile/test
  assertion that fails closed.
